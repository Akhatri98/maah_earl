      Twenty scenarios, and what they actually showed
      
    
      
      Our pitch said a bare LLM would be caught missing something, or
      inconsistent across runs. We built the experiment to test both
      halves, ran it live on Meta Muse, and recorded every transcript.
    
      
    
      
    
      
    
      Was it at least inconsistent?
      
    
      
    
      Why the tie, as far as we can tell
      
    
      
      One solve_load_case call returns all ten members' stresses.
      On a truss this small, “check everything downstream” and
      “check everything” are the same action, so the dependency walk
      has nothing to find that brute force does not. The traversal advantage
      is real in principle and is not demonstrated by this experiment.
    
      
    
      
      We could have handed the baseline a one-member-at-a-time solver and
      manufactured a gap. That is the exact dishonesty this project exists to
      catch, so we did not.
    
      
    
      What the run does establish
      
    
        
      
      • 22 of 22 unsafe members caught, zero false alarms, the same answer on all 60 runs — ours by construction, and provably so.
        • 
      
      • 9 of the 20 changes were genuinely safe and were approved. This is not a system that escalates everything and calls it caution.
        • 
      
      • And the guarantee on the bench tab, which no score can express: the model matched us at finding problems and still cannot decide that one ships.

      How it works
      
    
      Onshape change ─▶ DependencyGraph ─▶ walker ─▶ PyNite + Biject ─▶ Decision
                  (earl.ingestion)             (earl.analysis)
                                                     │ escalated
                                                     ▼
                                  SkyCiv report + cross-check (earl.artifacts)
                                                     │
                                                     ▼
                              ECN ─▶ Gmail / outbox (earl.delivery)
      

    
      What this page is really running
      
    
      
      Every change you compose is built by earl.eval.scenarios —
      the same module that builds our twenty eval scenarios — and run through
      earl.pipeline.run_pipeline, the same entry point the
      command-line demo uses. There is no demo-only shortcut behind this form.
    
      

    
      What it deliberately does not do
      
    
        
      
      • No model is called. A run here is a dependency walk and a solve. The eval numbers on the other tab come from transcripts recorded in Sprint 5A, not from a live call.
        • 
      
      • Nothing is written, sent, or merged. Stage 3 (SkyCiv) and Stage 4 (Gmail) are not a browser's to trigger. The notice is built and rendered for you to read.
        • 
      
      • The threshold floor is not a setting. You can raise the bar from this page. Lowering it below 1.0 reaches the same code a misconfigured .env would, and is refused there.
        • 
    
      

    
      The conventions that bite
      
    
        
      
      • SI everywhere inside the contracts (m, N, Pa). The benchmark's imperial numbers are converted once.
        • 
      
      • Two stresses on a material. yield_strength is 50 ksi; allowable_stress is the 25 ksi design allowable, and capacity comes from the allowable.
        • 
      
      • Statically indeterminate. That is why thinning one member pushes load into members nobody edited — and why nobody can tell by looking.
